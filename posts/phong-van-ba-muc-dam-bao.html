1

Consumer làm hai việc, không cùng lúc

Điều gì xảy ra nếu máy chết giữa hai việc đó?

Với mỗi message, consumer làm hai việc: xử lý nó (ghi database, gọi API, gửi email…), và , tức báo cho Kafka “đã xong tới đây”. Hai việc này luôn xảy ra lần lượt, nên máy có thể chết ở giữa.

Đời thường · đọc sách

Bạn đọc xong trang 42 rồi kẹp sách vào trang 43. Mai mở ra, bạn đọc tiếp từ chỗ kẹp sách.

Kafka · consumer

Offset đã commit chính là kẹp sách: Kafka nhớ nó, consumer khởi động lại sẽ đọc tiếp từ đó. Lưu ý: kẹp ở 43 nghĩa là message kế tiếp sẽ đọc là 43.

Ý chính

Ba mức đảm bảo chỉ là ba cách sắp thứ tự cho hai việc xử lý và dời kẹp sách. Chết ở giữa thì message bị bỏ qua hay bị làm lại là do thứ tự đó.

Ba mức, chạy thử từng bước

Chọn một kịch bản, bấm “Tiếp” (hoặc phím →) để xem consumer chết ở giữa.

MứcThứ tựChết ở giữa thìKafka docs

Ba câu định nghĩa trích nguyên văn tài liệu Kafka[1]; Confluent viết gần như y hệt[2]. Để ý chữ processed ở dòng cuối: “đúng một lần” là về kết quả, không phải số lần message bay qua mạng.

3

Vì sao at-least-once là mặc định

Mất và lặp đều dở. Sao lại chọn lặp?

Kafka guarantees at-least-once delivery by default, and allows the user to implement at-most-once delivery by disabling retries on the producer and committing offsets in the consumer prior to processing a batch of messages.

Apache Kafka 4.4 Documentation · Design

Message mất thì thường không ai biết để mà sửa. Tyler Treat viết về at-most-once: nếu bên nhận chết lúc xử lý, “that data is lost forever”, và “We must choose between the lesser of two evils, which is at-least-once delivery in most cases”[4]. Message lặp thì chống được ngay ở consumer. Chính tài liệu Kafka chỉ ra: “In many cases messages have a primary key and so the updates are idempotent (receiving the same message twice just overwrites a record with another copy of itself)”[1].

Ý chính

At-least-once luôn đi kèm một consumer (chống lặp). Chọn at-least-once mà quên chống lặp là đổi lỗi “mất” lấy lỗi “trừ tiền hai lần”.

Có khi nào nên chọn at-most-once?đào sâu

Có: log ứng dụng, số đo hiệu năng, sự kiện click. Mất vài bản ghi không sao, đổi lại đơn giản và không bao giờ lặp. Câu đúng là “thường chọn at-least-once”, không phải “luôn luôn”. suy ra

4

Bẫy auto commit: mất mà không ai biết

Bạn tưởng đang có at-least-once. Thật ra đang có at-most-once.

Consumer Java mặc định bật enable.auto.commit=true và commit khoảng mỗi 5 giây (auto.commit.interval.ms=5000)[5]. Nó commit những gì poll đã trả về, “whether you have finished processing them” hay chưa[6]. Nếu bạn xử lý xong hết rồi mới poll tiếp thì ổn. Còn đây là chuyện xảy ra khi bạn đẩy việc sang thread khác:

✗ Bẫy
// enable.auto.commit = true (mặc định)
val batch = consumer.poll(Duration.ofMillis(500))
batch.forEach { r ->
    executor.submit { handle(r) }
}
// poll lần sau có thể commit trước khi handle xong
✓ At-least-once rõ ràng
props["enable.auto.commit"] = "false"
while (running) {
    val batch = consumer.poll(Duration.ofMillis(500))
    batch.forEach { handle(it) }   // chống lặp!
    consumer.commitSync()          // xong hết mới commit
}

Javadoc dặn rõ: nếu xử lý ở thread khác thì “you must disable automatic commits and manually commit processed offsets for records only after the thread has finished handling them”[3].

Spring Kafka commit thế nào?đào sâu

Spring tự quản lý việc commit[7]: từ bản 2.3 nó tự đặt enable.auto.commit=false, và “The default AckMode is BATCH”, tức commit “when all the records returned by the poll() have been processed”. Với cấu hình mặc định, listener Spring cho bạn at-least-once. suy ra

AckModeCommit khi nào
BATCH (mặc định)khi đã xử lý xong cả lô mà poll() trả về
RECORDsau từng bản ghi, khi listener trả về
MANUAL / MANUAL_IMMEDIATEkhi code gọi acknowledge()
Bẫy phụ

Listener ném lỗi liên tục thì error handler mặc định thử lại (mặc định 10 lần) rồi ghi log và bỏ qua bản ghi đó[8]. Không cấu hình dead letter topic thì message đó coi như mất.

5

Exactly-once: làm được, nhưng có ranh giới

Khi nào transaction của Kafka cứu được, khi nào không?

Kafka gộp được hai việc vào một transaction vì offset của consumer cũng chỉ là một message trong một topic nội bộ[1]: “we can write the offset to Kafka in the same transaction as the output topics receiving the processed data”. Nhưng điều đó chỉ đúng khi đầu ra cũng là Kafka.

…can be used generally to provide exactly-once delivery when reading, processing and writing data on Kafka topics. Exactly-once delivery for other destination systems generally requires cooperation with such systems.

Apache Kafka 4.4 Documentation · Design

Đầu ra là database thì có hai đường (video “Kafka có exactly-once, vậy còn cần chống lặp không?” đã đi kỹ):

Đường 1 · phổ biến

At-least-once + consumer chống lặp. Ghi id của event vào bảng có khoá chính, cùng transaction DB với việc nghiệp vụ; gặp lại thì bỏ qua.

Đường 2 · ít gặp hơn

Lưu offset trong database. “letting the consumer store its offset in the same place as its output”[1]; khởi động thì seek tới offset đã lưu[3].

Code: đọc topic → xử lý → ghi topic, một transactionđào sâu
producer.initTransactions()                     // producer có transactional.id
while (running) {
    val batch = consumer.poll(Duration.ofMillis(500))
    producer.beginTransaction()
    batch.forEach { producer.send(ProducerRecord("orders-out", it.key(), transform(it.value()))) }
    producer.sendOffsetsToTransaction(nextOffsets(batch), consumer.groupMetadata())
    producer.commitTransaction()                // lỗi: abortTransaction() → output lẫn offset cùng huỷ
}

“These offsets will be considered committed only if the transaction is committed successfully”[9]. Consumer phía sau phải đặt isolation.level=read_committed (mặc định là read_uncommitted)[5]. Tính năng có từ Kafka 0.11.0.0 (28/06/2017), KIP-98[10].

“Kafka không có exactly-once.”
Có từ 0.11.0.0 (2017), trong phạm vi đọc → xử lý → ghi trên topic Kafka.
“Exactly-once nghĩa là message chỉ bay qua mạng đúng một lần.”
Là về kết quả: message có thể đến nhiều lần, nhưng kết quả như thể xử lý một lần. Tornow: exactly-once xử lý = at-least-once + bước xử lý idempotent[11].
“Bật auto commit là có at-least-once.”
Chỉ khi xử lý xong mọi bản ghi của một lần poll trước khi poll tiếp. Đẩy sang thread khác thì có thể mất.
“Dùng Spring Kafka thì không bao giờ mất message.”
Listener lỗi mãi thì sau 10 lần, error handler mặc định ghi log rồi bỏ qua bản ghi.
